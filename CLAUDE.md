## Git
- Do NOT commit unless I explicitly ask. Stage nothing automatically. When work is done, summarize changes and wait for my instruction.
- Never push without separate explicit approval, even if a commit was already approved.

## Build
- Before diagnosing any build/link error, use the verify-build skill.
- Project files are generated by premake - regenerate (`premake5 vs2022`, plus any extra flags like `--benchmarks` the target project needs) after adding, removing, or moving a source file, or after editing a premake5.lua.
- The LSP index (`compile_commands.json`) is separate from the premake project files and does not update on its own - run `premake5 export-compile-commands` after adding, removing, or moving a source file, or the LSP tool will be blind to it (stale/missing symbols, wrong "no references" results). Regenerating it is slow, so don't run it speculatively - only after an actual file add/remove/move.
- If you see missing-vendor-header errors, run `git submodule update --init --recursive` before editing code.
- A build failing with "error writing to program database" (locked .pdb) means the app or debugger is still running - ask me to close it, don't retry blindly.
- Verify both Debug and Release builds after changes to headers with config-dependent behavior (e.g. Debug.h-style macros).
- Use the Edit tool for source changes. Do not use sed with backreferences on C/C++ files.
